# Ручний план тестування CRM AeroKiDS

Це приймальний чекліст для staging перед кожним production merge. Позначайте `☐` під час тесту. У колонці результату вказуйте `OK`, `ПОМИЛКА` або `НЕ ЗАСТОСОВУЄТЬСЯ` і коротко записуйте, що побачили. Не використовуйте цей чекліст для записів на `crm.aerokids.space`.

## 0. Перед початком

- [ ] Відкрити саме staging URL з Render, перевірити, що в ньому є позначка `TEST / STAGING` або інша очевидна відмінність від робочої CRM.
- [ ] Переконатися, що адресний рядок не `crm.aerokids.space` і не production fallback `aerokids-crm.onrender.com`.
- [ ] У Render перевірити `/ready` тестового API; HTTP-відповідь успішна.
- [ ] Переконатися, що `VITE_API_URL` staging frontend указує на `aerokids-crm-api-staging`, а `DATABASE_URL` staging API — на `aerokids-crm-staging-db`.
- [ ] Перевірити, що SMTP/транзакційна пошта вимкнені. Тест не має надсилати листи, запрошення чи скидання пароля справжнім людям.
- [ ] Підготувати тільки вигадані дані з префіксом `TEST-<дата>`; не вводити дані реальних дітей, батьків, телефонів або оплат.
- [ ] Записати версію/commit staging deploy та час початку тесту.

## 1. Вхід і перший запуск

- [ ] Створити тестову організацію та першого власника через порожній стан CRM.
- [ ] Переконатися, що без правильного bootstrap key створення власника не проходить.
- [ ] Увійти правильними обліковими даними; після перезавантаження сесія зберігається згідно з налаштованим терміном.
- [ ] Вийти з CRM; захищені сторінки знову вимагають входу.
- [ ] Спробувати неправильний пароль і перевірити зрозуміле повідомлення без розкриття зайвих деталей.
- [ ] Перевірити, що перший запуск доступний тільки коли в тестовій базі ще немає організації/власника.

## 2. Навігація, вигляд, пошук

- [ ] Перейти по всіх пунктах лівого меню; назви, активний розділ і заголовок відповідають сторінці.
- [ ] Перевірити, що глобальний пошук початково компактний, розширюється під час введення, не перекриває екран модальним вікном і закривається доступною кнопкою.
- [ ] Знайти учня за ім’ям, прізвищем і телефоном; вибір результату відкриває саме його картку.
- [ ] Переконатися, що пошук показує відповідні групи/працівників/платежі, якщо вони є в результатах.
- [ ] Перевірити пошук без збігів, очищення запиту та закриття пошуку клавіатурою.
- [ ] Перемкнути світлу/темну тему та налаштування розміру тексту; після переходу між сторінками налаштування збережені.
- [ ] Перевірити контраст підписів, кнопок, меню, статусів і помилок; текст не обрізається і не зливається з фоном.
- [ ] Перевірити клавіатурне керування: `Tab`, `Shift+Tab`, `Enter`, `Escape`; фокус видимий.

## 3. Воронка заявок і дані учня

- [ ] Створити нову заявку з вигаданими дитиною, контактною особою, телефоном, джерелом, локацією та коментарем.
- [ ] Оновити сторінку; заявка й усі поля залишилися збережені.
- [ ] Відкрити картку та змінити кожне поле, яке редагується; після автозбереження значення не відскакує до старого.
- [ ] Змінити час пробного заняття; новий час лишається після перезавантаження.
- [ ] Додати двох окремих вигаданих дітей з різними даними та телефонами відповідальних осіб; обидві картки лишаються окремими.
- [ ] Додати братів/сестер із спільною контактною особою, якщо форма підтримує такий зв’язок; зміна одного учня не затирає дані іншого.
- [ ] Перевірити попередження про справжній дубль на тих самих даних; якщо система попереджає, але дозволяє окрему дитину — підтвердити потрібну дію.
- [ ] Перетягнути картку між етапами та повторити зміну через меню статусу; картка переходить у правильну колонку.
- [ ] Перезавантажити сторінку після статусної зміни; статус не повертається до попереднього.
- [ ] Перевірити всі дозволені статуси до та після зарахування: для зарахованого — активний, пауза, архів, повернути в роботу/очікує групу; недозволені переходи не показуються або коректно блокуються.
- [ ] Повернути активного учня в «Очікує групу»; запис зникає з активної групи там, де має, і з’являється в очікуванні без втрати історії.
- [ ] Перевірити «Повернутися пізніше»: дата/причина зберігаються, запис видно у відповідному фільтрі та він повертається у роботу належним чином.
- [ ] Перевірити скасування та видалення тільки на тестовій картці; підтвердження зрозуміле, сусідні учні не зачеплені.

## 4. Пробне заняття

- [ ] Створити пробне з картки учня та перевірити, що кнопка активна й форма відкривається.
- [ ] Заповнити дату, час, локацію, приміщення (якщо є) і відповідального працівника; зберегти та побачити пробне в розкладі й картці учня.
- [ ] Створити пробне без вибору локації, якщо у тестовій організації налаштована одна локація; перевірити очікуване автозаповнення/поведінку.
- [ ] Спробувати зайнятий час того самого працівника або приміщення; система показує конфлікт і не створює непомітне подвійне бронювання.
- [ ] Змінити час/дату пробного та перевірити збереження після повторного відкриття.
- [ ] Позначити, що дитина прийшла; перевірити наступні доступні дії.
- [ ] Позначити, що не прийшла; перевірити окрему дію для повторного запису/закриття та збереження причини, якщо вона вводиться.
- [ ] Після пробного перевести учня в очікування групи без примусового вибору групи.

## 5. Очікування, групи та зарахування

- [ ] Переконатися, що учні зі статусом «Очікує групу» видимі у воронці та в розділі/фільтрі очікування.
- [ ] Створити групу без учнів; зберегти її та побачити в списку.
- [ ] Призначити викладача; після вибору контроль зникає, а ім’я викладача можна натиснути, щоб змінити призначення.
- [ ] Створити групу з кількома днями тижня й різним часом для кожного дня; перевірити текст розкладу після збереження.
- [ ] Спробувати недопустимий крок часу/перекриття занять; система пояснює проблему і не зберігає некоректний розклад.
- [ ] Зарахувати учня з очікування в групу; статус, enrollment і склад учасників узгоджені після перезавантаження.
- [ ] Перевірити сумісність за віком, доступністю, локацією та часом; підказка відповідає введеним даним і пояснює конфлікт/частковий збіг.
- [ ] Спробувати перевести учня в іншу групу; перевірити підтвердження, стару й нову групу та збереження історії enrollment.
- [ ] Перевірити групу на межі місткості; не можна випадково перевищити встановлену межу.
- [ ] Перевірити індивідуальне навчання без групи та без прив’язки до локації, якщо цей сценарій доступний.

## 6. Розклад і заняття

- [ ] Перейти до розкладу та перевірити навігацію між днями/тижнями й підсвічування поточного дня.
- [ ] Створити розклад через одне меню додавання заняття/графіка; перевірити кілька днів і різний час.
- [ ] Перевірити, що створення групи не вимагає вдруге вводити її розклад, якщо він уже налаштований у розкладі.
- [ ] Створити заняття на майбутню дату та побачити його у правильному дні й часі.
- [ ] Відкрити заняття; перевірити групу, викладача, час, локацію та короткий склад учнів.
- [ ] Змінити дату/час заняття; зберегти, закрити та відкрити знову — зміна лишається.
- [ ] Перевірити накладання для групи, викладача, кімнати й локації; система показує точну причину конфлікту.
- [ ] Спробувати створити дубль заняття; система не створює другий однаковий запис непомітно.
- [ ] Переконатися, що минуле заняття й історична дата не змінюються при редагуванні майбутнього графіка.

## 7. Проведення занять і відвідування

- [ ] Відкрити конкретне заняття, не сторінку групи; відображається спрощений список учнів.
- [ ] Для кожного учня поставити «Є», «Нема» та «Поважна причина»; перевірити, що кожен стан можна зберегти.
- [ ] Ввести тему заняття та зберегти журнал; після повторного відкриття тема й відвідування присутні.
- [ ] Після збереження журнал відкривається в режимі перегляду; редагування доступне окремою дією.
- [ ] Позначити відсутність без поважної причини; заняття не списується автоматично, якщо встановлене правило каже рахувати за відвіданими.
- [ ] Позначити поважну причину; перевірити запис/можливість відпрацювання та узгодження з правилами групи.
- [ ] Звірити історію відвідувань учня з журналами занять; минулі записи не зникають.
- [ ] Перевірити повторне збереження журналу: не створюються дубльовані відвідування або повторне списання.

## 8. Тарифи, нарахування та оплати

Використовувати лише тестову організацію та нульові/тестові суми; жодних реальних оплат.

- [ ] Створити й відредагувати тестовий тариф; ціна вводиться з клавіатури, нуль не підставляється замість очищеного поля.
- [ ] Створити нарахування учню; кнопка працює, сума та період правильні.
- [ ] Додати часткову оплату; залишок боргу/переплати та історія платежів відповідають тестовій сумі.
- [ ] Позначити оплату повністю; статус, дата та сума видимі в картці й розділі фінансів.
- [ ] Перевірити повторне натискання/оновлення під час збереження; не створюються дубльоване нарахування або платіж.
- [ ] Змінити тариф посеред періоду: минулі заняття залишаються за старим тарифом, наступні рахуються за новим, переплата/борг пояснені зрозуміло.
- [ ] Перевірити повернення коштів/коригування, якщо доступно; первинний платіж не затирається, коригування має окремий запис.
- [ ] Запустити автоматичне поновлення лише на staging; повторний запуск не дублює нарахування.
- [ ] Перевірити нагадування про оплату; воно записується в CRM, але не надсилає справжніх повідомлень із staging.

## 9. Працівники, ролі та ізоляція організацій

- [ ] Створити тестового працівника та призначити роль/локацію.
- [ ] Увійти окремо під тестовими ролями owner/admin/manager/teacher/accountant, якщо вони створені; перевірити лише дозволені екрани та дії.
- [ ] Для викладача перевірити межі призначених груп і відвідувань; заборонена дія не має виконуватися тільки через приховану кнопку.
- [ ] Перевірити, що зміна/деактивація Staff синхронно змінює доступ membership і записується в аудит.
- [ ] Створити другу тестову організацію лише для перевірки tenant isolation; її учні/групи не з’являються в першій.
- [ ] Увійти під користувачем другої організації та перевірити, що перша організація недоступна.
- [ ] Перевірити помилкові прямі URL/API запити між організаціями; backend відмовляє, навіть якщо клієнт підміняє ID.

## 10. Аудит, звіти та приватність

- [ ] Перевірити звіт дашборду: заняття сьогодні, нові заявки, прострочені дії й оплати відповідають тестовим записам.
- [ ] Відкрити звіти за періодом/групою/статусом; перевірити фільтр дат та часовий пояс організації.
- [ ] Відкрити аудит після створення, редагування, статусного переходу, зарахування та оплати; подія містить правильного актора та об’єкт.
- [ ] Перевірити експорт приватності на тестовому учні; файл містить лише його дані й доступний тільки уповноваженій ролі.
- [ ] Перевірити список кандидатів на видалення/анонімізацію; реальні production записи не мають бути присутні в staging.
- [ ] Якщо перевіряється анонімізація — виконувати тільки на спеціальному тестовому учні та перевірити, що фінансова/аудит історія не руйнується.
- [ ] Запустити read-only invariant audit на staging; критичних порушень немає.

## 11. Мобільний та браузерний тест

Перевірити мінімум Chrome desktop і Chrome mobile/емуляцію ширини 360–390 px; для змін календаря/форм додатково перевірити Safari/iPhone, якщо доступний.

- [ ] Вхід, меню, пошук і кнопка виходу доступні без горизонтального прокручування.
- [ ] Воронка: картки читаються; переміщення та статуси доступні на дотику, а не тільки drag-and-drop.
- [ ] Картка учня та всі форми можна прокрутити й зберегти; клавіатура телефона не закриває активне поле чи кнопку.
- [ ] Пробне, календар, розклад і модальні/спливаючі панелі не виходять за межі екрана.
- [ ] Списки груп, учнів, платежів і журналів можна читати та фільтрувати на вузькому екрані.
- [ ] Перевірити світлу й темну тему на мобільному; контраст і видимість статусів достатні.
- [ ] Повернутися на попередню сторінку/закрити панель; стан і введені значення не губляться до натискання збереження.

## 12. Помилки, повторні дії та цілісність

- [ ] Надіслати форму з порожніми обов’язковими полями; помилки видно біля потрібних полів, дані не губляться.
- [ ] Ввести некоректний номер і некоректну дату/час; показана зрозуміла причина, запис не збережений.
- [ ] Під час збереження швидко натиснути кнопку двічі; створюється тільки один запис.
- [ ] Оновити сторінку після успішного збереження; серверні дані залишаються джерелом істини.
- [ ] Тимчасово перервати мережу/зупинити staging API; показується видиме повідомлення, UI не повідомляє про успішне збереження, коли сервер його не підтвердив.
- [ ] Після відновлення API повторити дію та переконатися, що попередня невдала спроба не створила прихований дубль.
- [ ] Перевірити багатокрокову дію (зарахування/переведення/оплата) на часткову помилку; пов’язані дані не лишаються в суперечливому стані.
- [ ] Перевірити часовий пояс: заняття, дата оплати та звіти показують локальний час організації, а не зміщений UTC час.

## 13. Коротка регресія для кожної маленької фічі

Після окремого тесту зміни кожного разу пройти цей мінімум:

- [ ] Увійти/вийти.
- [ ] Відкрити пошук і знайти тестового учня.
- [ ] Відкрити й відредагувати тестову картку, зберегти та оновити сторінку.
- [ ] Перевірити одну дію воронки, що стосується фічі.
- [ ] Перевірити пов’язаний запис у розкладі/групі/відвідуванні/фінансах.
- [ ] Перевірити той самий сценарій на мобільній ширині.
- [ ] Переконатися, що в консолі/мережевих запитах немає нової помилки.

## 14. Рішення перед production merge

Для кожної фічі зафіксувати:

- [ ] Номер PR у `crm-staging`, тестовий commit і Render deploy.
- [ ] Виконані номери сценаріїв цього плану та результат кожного.
- [ ] Скріншот або точні кроки для кожної помилки; записувати тестові ID, не персональні дані.
- [ ] Усі виправлення пройшли CI повторно та були повторно перевірені вручну.
